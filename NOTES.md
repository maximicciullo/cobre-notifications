## Context

Cobre has a **transactional, cloud-native, event-driven, microservices platform** that manages
client resources (accounts, payments, transactions) with full CRUD capabilities.

## Challenge scope (2 features)

### 1. Event notification delivery (webhooks)

Individually notify each event generated by the platform (e.g. balance update, event creation)
via **webhook to a specific URL**. Required capabilities:

- [ ] **Confirm subscription**: verify the event must be delivered to that client
      (mandatory: guarantee a client only receives notifications for its own events —
      isolation/authorization per client).
- [ ] **Delivery** of the notification to the configured URL endpoint.
- [ ] **Error handling with an efficient retry strategy**.
- [ ] **Store the final delivery information** for each attempt/result.
- [ ] **Near real-time observability**: the internal monitoring team must be able to detect
      behavior deviations and respond quickly to client complaints about delivery.

### 2. Event notification self-service API (REST)

Cobre wants clients to be able to self-query their notification events. The API must support:

- [ ] Query **all notification events per client**, filtering by `event creation date` and
      `delivery_status`.
- [ ] Get **a single notification event's details**.
- [ ] **Re-send (replay)** a notification when delivery has definitively failed.

## Candidate tasks

### Task 1 — System Design
- [ ] Design the full solution for both challenges (delivery + self-service API).
- [ ] Must ensure **scalability** and **resiliency**.
- [ ] Free format (document or presentation); free modeling framework (UML, C4, etc.).
- [ ] Be ready to justify every architectural decision in front of a panel (Q&A).

### Task 2 — API implementation
- [ ] **Hexagonal architecture**: mechanism to obtain the notification event and deliver it to
      the corresponding webhook via **HTTPS** to a specific URL (destination URL provided on
      presentation day — not available yet).
- [ ] **Java + Spring Boot**: implement the self-service API with these endpoints:
      - `GET /notification_events`
      - `GET /notification_events/{notification_event_id}`
      - `POST /notification_events/{notification_event_id}/replay`
- [ ] Use `challenge/notification_events.json` as seed dataset (10 sample events, fields:
      `event_id`, `event_type`, `content`, `delivery_date`, `delivery_status`, `client_id`).

### Task 3 — Security
- [ ] The API can be consumed publicly over the internet → identify **at least 3 OWASP Top 10
      vulnerabilities** that could impact it.
- [ ] Propose a **concrete mitigation** for each one.

## Deliverables and additional instructions

- [ ] Design document/presentation (free format and notation).
- [ ] **GitHub** repository for the implementation tasks — the **last commit must be before
      the delivery date**.
- [ ] Be ready to present and answer panel questions about architectural decisions.
- [ ] **AI usage is allowed and encouraged** — but must be **documented in detail** (prompts,
      screenshots, concrete use cases) in [`AI_USAGE.md`](./AI_USAGE.md).

## Data available

- `challenge/notification_events.json` — seed dataset with 10 sample events to load/test the
  self-service API.
- The real destination webhook URL **is not defined yet** — provided on presentation day, so the
  delivery mechanism must target a **configurable** URL.

## Decisions made (see [`DESIGN.md`](./DESIGN.md) for full rationale)

- Architecture: **Option B** — ambitious cloud-native design (Task 1, diagrams only) +
  simple, low-risk local implementation (Task 2), given the tight timebox (delivery
  2026-08-30).
- Language/framework: **Java 21 + Spring Boot 3**, hexagonal architecture.
- Storage: **PostgreSQL**.
- OWASP selection (Task 3): **A01 Broken Access Control, A03 Injection, A10 SSRF** — chosen as
  the 3 most feasible to actually implement and demo in the available time.
- Testing scope: unit tests for use cases/services, controllers, webhook adapter (WireMock),
  and retry/backoff logic. Integration tests (Testcontainers) as a later stage if time allows.

## Context

Cobre has a **transactional, cloud-native, event-driven, microservices platform** that manages
client resources (accounts, payments, transactions) with full CRUD capabilities.

## Challenge scope (2 features)

### 1. Event notification delivery (webhooks)

Individually notify each event generated by the platform (e.g. balance update, event creation)
via **webhook to a specific URL**. Required capabilities:

- [x] **Confirm subscription**: verify the event must be delivered to that client
      (mandatory: guarantee a client only receives notifications for its own events —
      isolation/authorization per client). — `DeliveryProcessingService` skips delivery when
      there's no active `Subscription`; A01 ownership is enforced on every read/replay.
- [x] **Delivery** of the notification to the configured URL endpoint. — `WebhookHttpAdapter`.
- [x] **Error handling with an efficient retry strategy**. — exponential backoff
      (`BackoffCalculator`) + dead-letter after `max_retries`.
- [x] **Store the final delivery information** for each attempt/result. — `DeliveryAttempt`
      (`status`, `retry_count`, `last_http_status`, `last_error`, `completed_at`).
- [x] **Near real-time observability** — Prometheus (5s scrape) + Grafana, pre-provisioned
      dashboard with 5 panels backed by custom Micrometer metrics (delivery outcomes, backlog,
      replays, dead-letters, API traffic). See README "Watch it in near real-time".

### 2. Event notification self-service API (REST)

Cobre wants clients to be able to self-query their notification events. The API must support:

- [x] Query **all notification events per client**, filtering by `event creation date` and
      `delivery_status`. — `GET /notification_events?created_from=&created_to=&delivery_status=`.
- [x] Get **a single notification event's details**. — `GET /notification_events/{id}`.
- [x] **Re-send (replay)** a notification when delivery has definitively failed. —
      `POST /notification_events/{id}/replay` (409 unless status is `FAILED`).

## Decisions made (see [`DESIGN.md`](./DESIGN.md) for full rationale)

- Architecture: **Option B** — ambitious cloud-native design (Task 1, diagrams only) +
  simple, low-risk local implementation (Task 2), given the tight timebox (delivery
  2026-08-30).
- Language/framework: **Java 21 + Spring Boot 3.5.3**, hexagonal architecture.
- Storage: **PostgreSQL**.
- OWASP selection (Task 3): **A01 Broken Access Control, A03 Injection, A10 SSRF** — chosen as
  the 3 most feasible to actually implement and demo in the available time.
- Testing scope: unit tests (39) for use cases/services, controllers, webhook adapter, and
  retry/backoff logic, **plus** integration tests (11, Testcontainers + WireMock) against real
  Postgres and a real HTTP call. 94% instruction coverage combined.
